# Рекомендатель v1

## API и параметры

```python
from reco_mvp.recommender import Recommender
model = Recommender({"min_support": 2}).fit(bundle, as_of="2026-06-01T00:00:00Z")
response = model.recommend("C001", k=3, strategy="hybrid")
```

Только стандартная библиотека Python 3.11+. `fit` читает Bundle в памяти,
не исходные файлы; возвращает `self`. Повторный fit полностью заменяет состояние.
Параметр `min_support` — положительное целое, по умолчанию 2. Неизвестные
параметры отвергаются. `recommend` до fit, неизвестная strategy, отрицательное,
нецелое или bool-значение k, неизвестный сегмент дают ValueError. k=0 даёт пустой
список. ID не преобразуются в числа; ведущие нули сохраняются.

## Время и общие фильтры

Все даты парсятся как timezone-aware datetime и приводятся к UTC. Обучение
учитывает строго `purchased_at < as_of`. Будущие транзакции не сохраняются в
состоянии модели. Известные только из будущей регистрации клиенты без покупок
до отсечения не сохраняются. Для клиента с known_since=null профиль допустим
при явном запросе, но наличие такого профиля не доказывает членство в исторической
когорте: когорту формирует evaluator. Историчность текущего segment не доказана.

Все стратегии исключают уже купленное, active=false, сегментно запрещённое и
available_from > as_of. Если available_from=null, товар допускается только при
продаже до as_of. Дата появления ровно as_of допустима. active=null не блокирует
товар, но сопровождается предупреждением. eligible_segments=null допускает товар
с предупреждением об отсутствии данных, а не о доказанной совместимости.
Пустой список eligible_segments не допускает ни одного сегмента. unknown-клиент
получает явно разрешённый unknown или товар с null-ограничениями.

Аргумент segment для существующего профиля должен совпадать с ним (включая
unknown), иначе ValueError. Для неизвестного ID допускается явный segment;
без него используется unknown. Пустой segment нормализуется в unknown.

## Стратегии

`popular`: сначала товары по числу уникальных покупателей в сегменте, затем
дополнение глобальной популярностью. Повторные покупки и quantity не увеличивают
популярность. Сегментная выдача — основной источник, is_fallback=false; глобальное
дополнение — true. Сортировка внутри источника: убывание числа покупателей,
затем product_id. Общая популярность не обгоняет сегментную.

`graph_only`: связи товаров, купленных одними и теми же клиентами, независимо
от заказа и даты внутри обучающего периода. Для каждой пары:

`cosine(a,b) = |buyers(a) ∩ buyers(b)| / sqrt(|buyers(a)| × |buyers(b)|)`.

Связь используется только при поддержке не менее min_support. Для каждой пары
сначала берётся сегментная связь; если она не проходит порог, берётся общая связь
с предупреждением и is_fallback=true. Для ранжирования используется
`score = max(cosine) × sqrt(support_count) × log(1 + buyers_all)`, где
`buyers_all` — число уникальных покупателей кандидата до даты отсечения.
Экспериментально можно заменить log(1 + buyers_all) на buyers_all ** p,
задав `popularity_exponent` в диапазоне от 0 до 1; значение по умолчанию
`None` сохраняет логарифмическую формулу. Например:
`Recommender({"popularity_exponent": 0.4})`.
Необязательный экспериментальный параметр `recency_weight` (по умолчанию 0)
домножает score на `1 + recency_weight × recent_buyers / buyers_all`.
`recent_buyers` — уникальные покупатели за `recency_days` до отсечения
(по умолчанию 120 дней); будущие покупки не используются. Экспериментальный
режим включается через `Recommender({"recency_weight": 1, "recency_days": 120})`.

Необязательный renewal-буст работает только при заполненном `product_group`
(см. CONTRACT.md) и усиливает кандидатов из уже купленных клиентом семейств:
`score ×= 1 + min(renewal_weight × log(1 + population_mass) ×
exp(−недели_после_последней_покупки_семейства / renewal_tau), group_bonus_cap)`,
где `population_mass` — число клиентов обучения, покупавших и товар-источник,
и кандидата внутри семейства. Параметры: `renewal_weight` (0 — выключен по
умолчанию, поведение идентично прежней версии), `renewal_tau` (недели,
по умолчанию 26), `group_bonus_cap` (по умолчанию 3). Причина выдачи
дополняется фразой о семействе. Часовые пояса, фильтр будущего и исключения
уже купленного действуют как для остальных связей.
При нескольких исходных товарах берётся максимальная cosine; source_product_ids —
все исходные товары с использованной
подтверждённой связью, в порядке product_id. support_count — мощность объединения
множеств покупателей этих связей, а не сумма. Сегментные и общие связи могут
использоваться для разных источников одного кандидата: support_count отражает
именно объединение использованных доказательств. Глобальный граф не является
популярным дополнением. Сортировка: убывание score, затем product_id.

Клиент запроса не исключается из заранее построенного offline-графа; однако
кандидат не входит в его прошлые покупки, поэтому клиент не может входить в
пересечение покупателей источника и кандидата. В численном знаменателе cosine
он может входить в покупателей источника. support_count для выдаваемого
co_purchase-кандидата подтверждён другими клиентами; это проверено тестом.

`hybrid`: сначала graph_only-кандидаты, затем сегментная и общая популярность
до k без повторов. Любая популярность в hybrid имеет is_fallback=true. Score
разных источников не складываются и не сравниваются: используется последовательный
приоритет. Поэтому score по итоговому списку hybrid может возрастать. Ни score,
ни cosine не являются вероятностью покупки.

## Предвычисления и сложность

Покупки хранятся как множества товаров по клиентам. Для графа обходятся только
пары реально купленных одним клиентом товаров, а не весь декартов каталог.
Пусть T — число строк, h_c — число различных товаров клиента, P — число товаров,
E — число поддержанных пар. fit: O(T + Σ h_c² + P log P) времени, память
O(T_unique + Σ h_c²) в худшем случае из-за сохранения множеств доказательств.
Хранятся сегментные и общие разреженные индексы, а не плотная P×P матрица.
Запрос обходит соседей исторических товаров, сортирует C кандидатов O(C log C),
объединяет их множества доказательств и при необходимости сканирует до O(P)
позиций готовых рейтингов популярности. Граф заново не строится на каждый запрос.
Ограничение истории не применяется: очень широкие истории имеют квадратичную
стоимость и требуют отдельного профилирования на реальных данных.

## Ограничения

Неполная история active, segment и каталога отражается в warnings. Вывод наследует
warnings данных. Новый товар без покупателей может пройти фильтры, но не получает
выдуманный score; обе модели не умеют его ранжировать. Недостаток кандидатов
даёт список короче k и предупреждение. Пустой graph_only не заполняется популярностью.
Для холодного старта hybrid использует только честную популярность. Объяснения
не обещают совместимость, экономию или дополняемость товаров. Продления, апсейл,
денежный эффект и превосходство над baseline не заявлены.
